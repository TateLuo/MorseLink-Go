## 1. 目标与范围

本文只聚焦“在线通联（QSO Online）”相关能力，不覆盖听抄训练、发报训练课程、版本更新 UI 等 PC 独有功能。

目标是回答三件事：
- PC 端在线通联已经做到什么程度。
- 嵌入式端当前已实现到哪一步。
- 在考虑嵌入式设备约束后，下一步应如何实现与改进。

## 2. PC 端在线通联基线能力（已实现）

基于 `gui/windows/qso_online.py`、`service/mqtt_client.py`、`utils/mqtt_query_tool.py`、`service/update_server.py` 的现状，PC 端在线通联具备：

1. MQTT 连接闭环
- 用户名/密码鉴权连接。
- 自动重连（指数退避）。
- 连接状态回调与 UI 状态同步。

2. 在线通联消息协议（v2 事件流）
- 发送按键事件，不直接发送解码文本。
- 典型字段：`eventType`、`eventSeq`、`myCall`、`pressedTime`、`pressedIntervalTime`、`senderDotTime`、`senderDashTime`、`senderLetterInterval`、`senderWordInterval`、`myChannel`、`eventTs`。

3. 同频道收发与侧频处理
- 主频道进行解码、显示、记录。
- 邻近频道做侧音/可视化队列处理。
- 通过 `eventSeq` 去重，过滤过期远端事件。

4. 实时反馈
- 发报/收报蜂鸣器反馈。
- 信号灯与可视化频谱/瀑布。
- 收发文本区与摩斯区实时刷新。

5. 通联记录
- 本地 SQLite `QSOrecord` 持久化。
- 记录查看、删除、可视化回放。

6. 在线人数显示
- 通过 HTTP API 查询在线人数并在页面刷新显示。
- 服务端通过 webhook 维护在线 client 集合。

## 4. 嵌入式与 PC 的关键差异（设计必须考虑）

1. 资源约束
- MCU RAM/Flash 有限，不适合直接复刻 PC 的重 UI、多线程和重对象模型。

2. 实时性与输入模型
- 嵌入式按键/编码器是硬实时输入，需优先保证按键时序精度与低抖动。

3. 功耗与电池策略
- 已有电池分级策略，通联业务必须可被低电策略降级或禁用。

4. 存储寿命
- 记录持久化不能高频直写 NVS，必须做批量或延迟刷写，控制磨损。

5. 离线优先
- 设备应在断网下保持核心可用，联网能力是增强而非单点依赖。

## 5. 建议的实现路线（按优先级）

## P0：最小互通闭环（已完成）

目标：两台嵌入式设备可在同频道实时收发并显示翻译，协议与 PC v2 对齐。

已实现事项：
- 新增 QSO 业务配置字段：`myCall`、`qsoChannel`、`qsoTopic`，并接入 AP 配网页与持久化。
- `main.cpp` 已绑定 `MqttManager::setMessageCallback(...)`，建立收报入口并订阅 `qsoTopic`。
- `lib/CWEngine` 已实现：
  - 发报/收报时序判定（点划、字间隔、词间隔）。
  - 间隔清洗（`max(word_gap*6, 6000)`）。
  - 事件去重（`senderCall + eventSeq`）。
  - Morse token 解码（`A-Z0-9`）。
- 主界面 RX/TX 已切换为真实通联流，统一格式：`RX/TX: <morse> | <text>`。
- 发送策略已按实时事件处理：MQTT 断连直接丢弃 KEY 事件，不走离线重放。

验收标准：
- 同频道两端可看到同步的摩斯符号与翻译文本。
- 断网重连后可恢复收发。
- 本地按键体验无明显时序漂移。

## P1：可靠性与可运维

目标：把“能用”提升到“稳定可长期运行”。

建议事项：
- 引入 QSO 会话管理（开始/结束、方向、持续时长）。
- 增加轻量记录持久化（建议环形文件或批量 NVS 写入）。
- 增加协议字段校验与异常包统计（便于现场排障）。
- 增强 AP 配网页参数校验（呼号格式、频道范围、主题合法性）。

验收标准：
- 连续运行 24h 无明显内存增长和死锁。
- 记录可查询，且写入频率受控（避免 flash 过度磨损）。

## P2：增强能力

目标：补齐体验差距，但保持嵌入式可承受复杂度。

建议事项：
- 在线人数方案优先改为 MQTT Presence（retain/last seen），避免设备频繁 HTTP 轮询。
- 侧频能力做“简化版”实现（不追求 PC 级多通道可视化）。
- 增加诊断页：网络状态、MQTT RTT、丢包/重连计数。

验收标准：
- 在线状态可观测。
- 功耗和内存开销在可控范围内。

## 6. 推荐的模块分工（贴合当前工程）

- `lib/CWEngine`：点划判定、间隔判定、协议编解码、去重。
- `lib/MqttManager`：主题订阅、发布、离线队列、连接态事件。
- `lib/UIController`：RX/TX 字段真实数据驱动与通联状态展示。
- `lib/ConfigManager`：新增 QSO 相关配置持久化。
- `src/main.cpp`：串联输入、通联业务、网络状态、电池策略优先级。

## 7. 后续建议执行顺序（P1/P2）

1. 增加通联记录持久化（环形缓存 + 受控刷写），避免掉电丢失。  
2. 增加协议异常统计与诊断页（重连次数、发布失败、去重命中）。  
3. 增加长时稳定性治理（10min/24h 内存与任务健康监测）。  
4. 设计轻量在线状态方案（MQTT Presence），替代 HTTP 轮询。  
5. 评估侧频“简化版”实现边界，控制 RAM/CPU 开销。
